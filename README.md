## Алхам 3: SLO

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл | Үндэслэл |
|----------|------------------|-------|---------------|----------|
| Performance | `/cart/add` latency | p95 < 10 ms, p99 < 25 ms | 20 VU тогтмол, 1 мин | Бодит p95 1.7 ms, p99 5 ms. ~5 дахин нөөцтэй, хэвийн хэлбэлзлийг даах ч жинхэнэ удаашралыг барина. Зааврын 200 ms нь 100 дахин сул тул юу ч хэмжихгүй |
| Reliability | `/pay` error rate | < 8% | 20 VU, 1 мин | 5% алдаа суулгасан. ~930 хүсэлтэд санамсаргүй хэлбэлзэл ±0.7% тул 8% нь ~4σ нөөц |
| Availability | Бүх хүсэлтийн амжилтын хувь (checks) | > 90% | 20 VU, 2 мин, 10 s зогсолттой | 2 минутад 10 s зогсолтыг (8.3%) тэвчих хэмжээний бодит босго |
| Нэмэлт: Report | `/report` latency | p95 < 450 ms | 20 VU, 1 мин | Дизайнаар max 400 ms, бодит p95 389.62 ms. Ачааллын үеийн event loop-ийн хоцрогдлын нөөц 50 ms |

### Error budget (цагаар)

Availability SLO 90%, цонх 2 минут (120 s):

    Error budget = 120 s × (1 − 0.90) = 12 s "эвдрэх эрх"

Анхаарах зүйл: хэвийн үед ч checks 98.10% (`results/probe.txt`) байсан. Учир нь `/pay`-ийн 5% алдаа нийт хүсэлтийн ~1.9%-ийг эзэлдэг. Тэгэхээр budget-ийн ~1.9 нэгж хувь нь crash-гүйгээр аль хэдийн зарцуулагддаг. Цэвэр зогсолтод ногдох хэсэг нь ойролцоогоор 8.1% буюу ~9.7 s болно. Хүсэлтээр тооцсон budget-ийг Алхам 5-д харьцуулна.

## Алхам 5: Мини chaos

**Арга:** серверийг арын горимд асааж, 40 секундын дараа `kill -9` (SIGKILL) дохиогоор гэнэт унагааж, 10 секундын дараа дахин асаав. Эхэндээ Ctrl+C-тэй ижил SIGINT дохиог ашиглах гэж оролдсон ч bash-ийн арын процесс SIGINT-ийг үл тоомсорлодог тул сервер унаагүй. SIGKILL-ийг процесс барьж авах боломжгүй тул бодит crash-тай хамгийн адил. Цагийн бичлэг: `results/chaos-server.txt`

    СЕРВЕР АСАВ: 21:47:52
    СЕРВЕР УНАВ (SIGKILL, crash): 21:48:32
    СЕРВЕР ДАХИН АСАВ: 21:48:42

Зогсолт **10 s**. Процесс асмагц гар оролцоогүйгээр хариу өгч эхэлсэн тул сэргэх хугацааны шаардлага (≤ 10 s) хангагдсан.

**k6-ийн үр дүн** (`results/chaos.txt`, 20 VU, 2 мин, **`exit=99`**):

| Threshold | Босго | Бодит | Үр дүн |
|-----------|-------|-------|--------|
| `checks` (availability) | rate>0.90 | **87.73%** (5006/5706) | ✗ |
| `http_req_failed{name:pay}` (reliability) | rate<0.08 | **15.19%** (289/1902) | ✗ |
| `http_req_duration{name:cart}` | p(95)<10 | p95 = 1.72 ms | ✓ |
| `http_req_duration{name:report}` | p(95)<450 | p95 = 390.92 ms | ✓ |

Check тус бүрийн алдаа: cart 202, report 209, pay 289. Хэвийн үед cart, report-д алдаа 0 байсан.

### Бодит availability (хүсэлтээр) ба error budget

    Availability = амжилттай / нийт = 5006 / 5706 = 87.73%   → SLO (90%) зөрчигдсөн
    Хүсэлтээр тооцсон budget = 5706 × 10% ≈ 571 алдаа
    Бодит алдаа = 700                                         → budget ~129 хүсэлтээр хэтэрсэн

**Цагаар тооцсон 12 s-ийн budget яагаад хүсэлтээр зөрж байна вэ:** цагаар бол 10 s / 120 s = 8.33% зогсолт, availability 91.67% болж PASS байх ёстой. Гэвч k6-ийн `checks` бол ЦАГИЙН биш ХҮСЭЛТИЙН хувь:

1. Сервер унасан үед хүсэлт `connection refused`-ээр агшин зуур буцаж, `/report`-ын 200–400 ms хүлээлт алга болдог. Давталт ~1.3 s-ээс ~1.0 s болж богиноссон (`iteration_duration min=1s`). Ийм учраас зогсолтын 1 секунд хэвийн секундээс олон хүсэлт "иддэг". 2 минутад 1902 давталт хийгдсэн бол хэвийн хурдаар (`pass.txt`: 1 минутад 929) ~1858 байх ёстой.
2. Зогсолтоос үүдсэн алдаа ойролцоогоор cart 202 + report 209 + pay ~204 ≈ 615 буюу нийт хүсэлтийн ~10.8%. Энэ нь цагийн 8.33%-иас их.
3. Хэвийн үед ч `/pay`-ийн 5% алдаа budget-ийн нэг хэсгийг (~1.7 нэгж хувь) аль хэдийн зарцуулдаг.

**Reliability яагаад зэрэг FAIL болов:** сервер унасан үед `/pay`-ийн хүсэлт бүр унасан (status 0) тул нэг эвдрэл availability болон reliability хоёр SLO-г зэрэг зөрчсөн. **Тусгаарлах арга:** reliability SLI нь зөвхөн сервер буцаасан `500` хариуг, availability SLI нь зөвхөн холбогдож чадаагүй (status 0) хүсэлтийг тоолох ёстой.

## Алхам 6: Threshold-оо зориуд эвдэх

`slo-test-fail.js`: `/report`-ын босгыг `p(95)<100` болгосон (жинхэнэ SLO 450 ms). Сервер 200 ms-ээс хурдан хэзээ ч хариулдаггүй тул ямар ч машин дээр найдвартай FAIL болно. Эх файл: `results/fail.txt`

    ✗ 'p(95)<100' p(95)=388.9ms
    level=error msg="thresholds on metrics 'http_req_duration{name:report}' have been crossed"
    exit=99

FAIL-ийг `✗` тэмдэгтэй threshold-ийн мөр болон `level=error` мөр харуулж байна. Бусад гурван threshold ✓ байсан ч нэг нь унахад k6 **exit code 99** буцаадаг. CI pipeline үүнийг 0 биш гэж хараад build-ийг зогсооно. (Анхаар: `echo $?` нь pipe-ийн дараа `tee`-ийн кодыг буцаадаг тул k6-ийн жинхэнэ кодыг `${PIPESTATUS[0]}`-ээр авсан.)

`/cart/add`-ийг `p(95)<50` болгосон бол PASS хэвээр үлдэх байсан. localhost дээр сүлжээний хоцрогдол байхгүй, endpoint ямар ч ажил хийдэггүй тул p95 нь ~1.5 ms. Иймээс 50 ms ч гэсэн бодит утгаас 30 дахин сул.

## Дүгнэлт

1. Сценарио → SLO → threshold шилжилтийн хамгийн хэцүү хэсэг нь **бодитой босго сонгох** байлаа. Зааврын жишээ `p(95)<200` нь `/cart/add`-ийн бодит 1.7 ms-ээс 100 дахин сул тул юу ч хэмжихгүй байсан. Тиймээс эхлээд `probe.js`-ээр хэмжиж, дараа нь босгоо тогтоосон.
2. Хоёр дахь хэцүү зүйл нь **availability-г юугаар хэмжих** вэ гэдэг байв. Сценариод "цаг" гэж бодсон ч k6-ийн `checks` хүсэлтийн хувийг хэмждэг.
3. Хэвийн ачаалалд (`results/pass.txt`) дөрвөн SLO бүгд хангагдаж, `exit=0` гарсан.
4. Chaos туршилт availability сценариогийн **сэргэх хугацааны** хэсгийг баталсан: 10 s зогсолтын дараа сервер гар оролцоогүйгээр шууд хариу өгсөн.
5. Харин **availability ≥ 90%** гэсэн хэмжүүрийг **үгүйсгэсэн**: хүсэлтээр 87.73% гарч, budget 571-ийн оронд 700 алдаа гарсан.
6. Цагаар тооцвол 91.67% болж PASS байх байсан. Энэ зөрүү нь "зогсолтын үед хүсэлт хурдан унаж, олон хүсэлт иддэг" гэдэгтэй, мөн `/pay`-ийн суурь алдаа budget-ийг урьдчилан иддэгтэй холбоотой.
7. Иймд 2 минутын богино цонхонд 90% SLO нь 10 s зогсолтыг тэвчих хэмжээний **хэт өөдрөг** байсан. Бодитойгоор бол SLO-г ~85% болгох, цонхыг уртасгах, эсвэл зогсолтыг богиносгох хэрэгтэй.
8. Нэг crash availability болон reliability хоёр SLO-г **зэрэг** зөрчсөн нь SLI-ийг тодорхой ялгах ёстойг харуулав (500 хариу ба холболтын алдааг тусад нь тоолох).
9. Зориуд эвдсэн threshold `exit=99` буцаасан нь SLO-г CI-д quality gate болгох механизмыг бодитоор харуулсан.
10. Хамгийн чухал сургамж: SLO-г цаасан дээр биш хэмжилт болон эвдрэлийн туршилтаар баталгаажуулах хэрэгтэй. Эс тэгвэл цагаар зөв мэт харагдах тоо хүсэлтээр зөрчигдсөн байж болно.
